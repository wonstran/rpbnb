The response correctly resolves both prior findings: the balanced layout guarantees exactly `C` nonempty chunks, and the plan now explicitly connects the measured chunked slope to default-budget generation. Two resolver edge cases remain.

## Findings

### [P1] Separate static/chunked calibrations need path-specific budgeting, not one chunk-derived unit budget

The plan still permits two outcomes after calibration:

1. separate static and chunked slopes/weights; or
2. one component-wise conservative constant set.

The shared conservative option is coherent. The separate option is not yet fully specified because `.resolve_tape_chunks()` uses chunked constants to decide the layout—including whether `C == 1` and the static graph will run—and the default `max_workload` unit count is derived from the chunked slope. This is safe only if measurements prove the chunked slope and family weights dominate the static graph for every family/thread mode. The extra mask operations make that plausible globally, but relative family weights can change, and the plan explicitly treats measurement as authoritative rather than assuming ordering.

If, for any family, the static graph's predicted peak exceeds the chunked prediction at the same `n × R`, the resolver can select `C = 1` under a budget derived from the cheaper chunked calibration and run a static tape above the advertised memory limit.

Choose one explicit contract:

- Prefer the already-described shared constant set, taking conservative maxima across both graphs for the slope and each family/mode weight. One `max_workload` unit then has one meaning on every branch.
- If separate constants are retained, resolve in bytes/path space: test the `C = 1` candidate with static constants against the memory budget, and only after rejecting it compute a chunked layout with chunked constants. Define how an explicitly supplied unit-valued `max_workload` maps to both calibrations without changing its documented meaning silently.

Add a regression fixture where the larger measured/pinned calibration alternates between static and chunked paths, proving neither branch can be selected above budget. The current default-control test covers chunked derivation but not safe selection of the static branch.

### [P2] Preserve the documented `max_workload = Inf` opt-out explicitly

The current guard short-circuits on `Inf`. The new resolver pseudocode proceeds to
`draws_per_chunk_max = floor(max_workload / one_draw_workload)` and derives `C`; with `Inf`, a literal `ceiling(R / Inf)` calculation produces zero rather than the required one-chunk static path. The plan does not state a special case.

Specify and test:

- `tape_chunks = NULL`, `max_workload = Inf` → `C = 1`, `chunked = 0`, no guard message.
- user-pinned valid `tape_chunks`, `max_workload = Inf` → honor the pinned balanced layout without a budget error.
- the one-draw hard stop is bypassed when the user explicitly disables the guard, matching today's contract.

This keeps `Inf disables this guard` true after `.check_tmb_workload()` is replaced.

## Disposition

The balanced padding and default chunked-budget plumbing are accepted. The remaining P1 is a calibration-branch ambiguity rather than an algorithmic flaw; selecting the shared conservative constant option would resolve it cleanly. The `Inf` behavior is a small but user-visible compatibility requirement.
