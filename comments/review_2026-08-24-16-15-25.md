# Second follow-up review: TMB SML OOM plan response

Reviewed `comments/response_2026-08-24-16-02-09.md` against the latest plan and the current workload calibration.

The response resolves all five findings from `review_2026-08-24-15-54-38.md`: the padded single-tape layout is mathematically sound, fit-time validation is correctly placed, the wrapper methods now describe one full objective, the unchunked branch is separated, and the bookkeeping is corrected. Two memory-accounting gaps remain in the revised plan, followed by one verification-contract correction.

## Findings

### [P1] The `n × C` pass-1 cache can exceed the memory budget even when the tape passes

The plan still caches every chunk's `obs_loglik` in an `n × C` R matrix but models peak memory only as the single TMB tape of size `n × ceiling(R/C)`. These quantities move in opposite directions: making chunks smaller reduces the tape while increasing `C` and therefore the cache. At the extreme `Rc = 1`, the cache is `n × R`, recreating a large full observation-draw allocation on the R side.

A concrete default-budget case shows this is not merely asymptotic. For Famoye with sequential taping, the current 8 GiB calibration admits roughly 700,000 weighted observation-draw units. With `n = 500,000` and `R = 5,000`, a one-draw tape passes the hard-stop test, so auto resolution can choose `Rc = 1`, `C = 5,000`. The cached matrix then contains 2.5 billion doubles—about 20 GB before R's allocation overhead—so the guard authorizes an OOM despite the TMB tape itself fitting.

Prefer an O(n)-memory streaming design:

1. In `fn(par)`, stream across chunks and update the per-observation full log-sum-exp accumulator without retaining all `log S_ic` columns.
2. In `gr(par)`, use the cached full per-observation denominator but rerun `report(par)` for each chunk to recover that chunk's numerator/weight before its `obj$gr(par)` call.

This costs one additional serial report sweep when `fn` and `gr` are both requested, so include it in the runtime benchmark. A bounded hybrid cache is also possible, but then the resolver must reserve explicit bytes for it and switch to streaming before `n * C * 8` threatens the process budget. Update the peak formula, message, memory tests, and RDS/cache tests accordingly.

### [P1] The workload constant is calibrated on the static graph, not the chunked mask-aware graph

The static `chunked = 0` branch preserves the old tape, but the guard proposes using the same post-Phase-1 `peak_bytes_per_unit` for `chunked = 1`. The chunked graph adds dynamic `Z`, per-observation `w`, and—most importantly—`draw_w(r) * exp(...)` inside every observation-draw reduction. That mask multiplication is O(n × Rc), so its tape/peak slope is not guaranteed to match the static branch. The existing `inst/tmb_benchmark_memory.R` builds the ordinary unchunked objective; simply rerunning it after Phase 2 measures the wrong graph for auto-chunk safety.

Add explicit chunked-mode memory calibration for every family (including padded and all-valid masks, plus the supported thread/tape modes). Either publish a separate conservative `chunked_peak_bytes_per_unit`/family-weight set used by `.resolve_tape_chunks()`, or prove from measurements that one shared upper bound covers both graphs and set the constant to the larger slope. The memory regression should feed the actual guard constant, not remain only an informational C=4 comparison. Until that is measured, do not claim that `n × Rc` maps to the same calibrated process peak as the static tape.

### [P2] “Bitwise equal to current code” conflicts with Phase 1's algebraic rewrites

The new static branch can make Phase 2's `C = 1` path identical to the **post-Phase-1** path, but the plan's test (j) says it will be bitwise equal to the current implementation. Phase 1 replaces `dnbinom2`/`dpois`, hoists terms, and changes operation ordering; its own fixture contract allows differences around 1e-12. Those changes can alter final bits before chunking is introduced.

Define the checkpoint explicitly: capture/verify the Phase-1 static baseline, then require Phase 2 with `chunked = 0` to match that baseline (bitwise if the spike demonstrates it, otherwise at the established tolerance). Keep the original-current-code comparison under Phase 1's algebraic-equivalence tolerance. This avoids an impossible combined-phase assertion and makes a failure attributable to the correct phase.

## Disposition

The padded single-object algorithm is suitable once total wrapper memory and the chunked graph's measured peak slope are part of the guard. Both P1 items are blocking for an OOM-prevention feature because either can still let the resolver approve a process peak above its advertised budget.
