## P0 — Laplace Famoye validated against Halton draws not in its likelihood

**Accepted; fixed, and further than requested.**

Your numbers reproduce exactly. With one Normal random coefficient per margin,
`beta = 0`, `sd = 0.2`, `m = 0.5`:

```text
  5 Halton draws  -> [-2.550287, 3.131312]
400 Halton draws  -> [-2.142173, 2.752759]
latent support    -> [-1, 1]
lambda = 2: admissible under the Halton box, INVALID for Laplace
```

Your reasoning about the latent support is right, and I confirmed each step
rather than taking the conclusion: `c_val(mu, m) -> 1` as `mu -> 0` and `-> 0`
as `mu -> Inf`, so an unbounded latent makes `c` span `(0, 1)` in each varying
margin.

**Your minimum ask was to return `NA` with a warning on this path. I did not do
that, because a better answer is available and cheap.** Both quantities bounded
by `lambda_bounds_vec()` are pointwise maxima of *bilinear* functions of
`(c1, c2)`. A bilinear function on a box attains its extremum at a vertex, and a
pointwise max of such functions is maximized at one of their vertices, so the
supremum over the attainable `c`-rectangle is attained among its corners.
Enumerating those corners is therefore **exact**, not a sample — no `NA`
needed. A new `.lambda_bounds_latent()` does that, per observation.

Two consequences worth stating:

1. **This fixes the objective, not just the check.** Under Laplace the frozen
   `lamLo`/`lamHi` handed to the template were *also* computed from the Halton
   grid, so the constraint the Laplace Famoye likelihood was optimized under was
   itself too wide — a defect strictly worse than the mis-validation you found,
   and inherited from `rpbnb.tmb` rather than introduced in `a6f2d87`. The
   estimator-specific bound is now used for both the frozen bounds and the
   post-fit re-check, so the constraint a fit is judged against is the
   constraint it was optimized under.
2. **When both margins carry a varying random coefficient the Laplace bound is
   `[-1, 1]` and parameter-independent**, so the entire frozen-versus-current
   problem — the first review's P0 — *does not arise on that path at all*. It
   reappears only when a single margin varies, because the other margin's `c`
   is then a function of the parameters; the re-check still covers that case.
   Verified: `[-1, 1]` at both start and optimum with both margins random;
   `[-1.732015, 1.732015]` with one, which is exactly
   `1/max(c, 1-c)` at `c = c_val(1, 0.5) = 0.5773623`.

On the conservative direction: treating a varying margin as spanning the full
`(0, 1)` is exact for Normal coefficients and an over-approximation for
lognormal, whose deviation is unbounded on one side only. That is conservative
in the safe direction — a wider `c`-range yields a *narrower* lambda interval,
so the check can only reject more, never fewer. Laplace supports only these two
distributions, so no other case arises.

The SML path is unchanged and keeps the finite-draw bound, which is the correct
notion there: the SML likelihood genuinely is an average over those draws, so
the joint pmf only has to be non-negative at each of them.

`test-laplace.R` gains two tests: one asserting the estimator-specific bounds
(Laplace `[-1, 1]`, parameter-independent; SML strictly wider) and one for the
single-varying-margin case.

**Not fixed:** the SML path still freezes its bounds at the starting values.
That is the first review's P0 and remains open, with detection only.

## P1 — Non-Normal scales mislabeled as standard deviations

**Accepted; fixed.** You are right, and this is a real gap in my previous fix: I
removed the invalid Wald test and then left the mislabeling in place, which
means the row still asserted something the model does not estimate. `exp(log_w)`
is a uniform/triangular half-width and `exp(log_s)` is a lognormal log-scale;
neither is a coefficient SD, and rewriting every row to `sd1:`/`sd2:` under a
heading reading "Random-coefficient SDs" invited exactly the wrong reading.

The heading is now "Random-coefficient scales", and each row keeps its own
label. Rather than a lookup, the label comes from stripping `log_` off the
parameter name — which is itself constructed from `rand_dist_registry`'s
`scale_label` — so a new distribution's label follows automatically and cannot
drift from the registry. A note under the block states what `sd`, `w` and `s`
each mean.

Verified on a uniform random coefficient: the row prints as `w1:x1`, no `sd1:`
appears, and the heading no longer says "SDs".

On your closing suggestion — transforming to actual coefficient SDs with the
distribution-specific formula and delta method — I have not done that. It is a
genuine feature (a uniform half-width `w` has SD `w/sqrt(3)`; lognormal has
`exp(mu + s^2/2) * sqrt(exp(s^2) - 1)`, which also depends on the location) and
worth having, but adding derived quantities with their own delta-method SEs is
new inference surface rather than a labeling correction, and it should be
specified and tested as such. Labeling honestly is the fix for the defect;
reporting SDs is a separate request. Say the word if you want it.

## P2 — Suffix search falls back to overwriting

**Accepted; fixed.** Confirmed: `for (i in 2:1000L)` with every name taken exits
without assigning `output_path`, and the write then replaces the unsuffixed
original with no warning — reintroducing the exact defect the guard exists to
prevent, in the one case it was built for.

An exhausted search now errors. I chose erroring over your alternative of
continuing until a free name is found: at a thousand same-second collisions the
situation is not a naming problem to be worked around but a sign that something
is wrong with the caller or the directory, and silently walking to `-100000`
would bury that. The message names the exhausted stamp, the limit, and the
directory.

Verified: the call errors with "Refusing to write", and a sentinel in the base
file survives. `test-results-export.R` gains that case plus the ordinary
single-collision case (suffixed to `-2`, warning raised, base preserved).

On atomic reservation for concurrent writers: not implemented. Nothing in the
package writes these reports concurrently — they are produced one per fit by
analysis scripts — so a `file.exists()` race is not currently reachable, and I
would rather not add lockfile machinery for a hazard that no caller can trigger.
It is the right fix if that changes.
