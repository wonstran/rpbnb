## Verdict

The shared support helper removes the finite-draw parameter space from the Normal two-margin fixtures in both engines, and deriving the mean support before the numerical `eta` clamp fixes the previous extreme-dispersion defect. Two correctness issues remain in the Rcpp integration: the retained upper scale clamp is unsafe for bounded random-coefficient distributions, and parameter-dependent bounds are recomputed by the objective while omitted from the gradient supplied to the optimizer.

## Findings

### P0 - The upper scale clamp widens the bound for Uniform and triangular coefficients

**Locations:** `R/rpbnb_likelihood.R:40-43`, `R/rpbnb_likelihood.R:100-110`, `R/halton_parallel.R:41-55`, `R/halton_parallel.R:133-149`, `R/fit_rpbnb.R:327-348`; compare `R/famoye_core.R:149-190` and `comments/response_2026-08-08-11-31-05.md:52-57`.

The response says the retained scale clamp “cannot widen the admissible set” and “only decides whether a coefficient varies at all.” That is true for an unbounded Normal support, but false for the bounded distributions the new shared helper explicitly handles. Uniform and triangular deviations have support `[-s,s]`; reducing `s` with the upper `log_scale <= 20` clamp shrinks the attainable mean range and therefore can widen the lambda interval.

This is a direct mismatch in the default Rcpp engine. Its likelihood realizes coefficients with raw `s = exp(log_scale)`, but its support-bound adapters use `exp(clamp(log_scale, -20, 20))`. A base-R reproduction with one Uniform coefficient in each margin, `log_w = 30`, loading `x = 1e-9`, zero fixed slopes, and `m = 0.5` gives:

```text
bound computed with exp(20): [-2.0362897, 2.5327946]
actual exp(30) support:       [-1.0000000, 1.0000000]
```

Thus `lambda = 2` is admitted by the bound handed to the likelihood even though the stated coefficient support contains regions where the Famoye PMF is negative. The lower scale floor is conservative for bounded distributions, but the upper cap is permissive; they cannot be treated as one harmless operation.

Use the unclipped theoretical scale in the support calculation for Uniform and triangular coefficients. If an underflow floor is retained so a declared tiny scale does not become exactly zero in R, do not pair it with an upper cap. Add a regression with a bounded distribution and an above-cap log-scale; the current cross-engine test uses only ordinary Normal coefficients and cannot detect this defect.

### P1 - The Rcpp optimizer receives a gradient of a different objective when support bounds move

**Locations:** `R/rpbnb_likelihood.R:93-118`, `R/halton_parallel.R:98-123`, `R/famoye_core.R:171-205`; tests deliberately freeze the interval at `tests/testthat/test-fit-rpbnb.R:12-31` and `tests/testthat/test-rpbnb-likelihood-dist.R:18-46`.

For a single varying margin or bounded Uniform/triangular coefficients, `famoye_support_bounds()` depends on `beta`, dispersion, and/or scale. The R and C++ wrappers recompute that interval on every objective call, so the actual optimized function contains derivatives of `lamLo(par)` and `lamHi(par)`. The analytic gradient returned from the likelihood kernel treats the supplied interval as fixed and omits those terms.

The updated numeric-gradient tests do not validate the gradient consumed by the optimizer: they compute the bounds once, call a separate fixed-bounds objective, and compare its numeric gradient with the frozen-bound analytic gradient. The OPG score identity is likewise insufficient because the scores and analytic gradient omit the same bound derivatives.

This mismatch reproduces without package dependencies. For a 20-observation, one-margin Uniform random-coefficient fixture, a central finite difference of the actual `bnbr_rp_ll_and_grad()` wrapper differed from its attached analytic gradient by as much as `0.463054`; the `beta`, log-scale, and dispersion coordinates were affected, while `z_lambda` agreed because the bounds do not depend on it. The optimizer is therefore being directed by a vector that is not the derivative of the function it evaluates.

Either include the support-bound derivatives in the Rcpp gradient (with explicit handling of corner changes), or make the optimization objective genuinely fixed-bound and perform the same post-fit validity check used by TMB. Add a numeric-gradient test around the actual moving-bound wrapper for a parameter-dependent specification; retaining only frozen-reference tests codifies the mismatch rather than guarding the optimizer contract.
