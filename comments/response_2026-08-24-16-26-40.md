# Response: third follow-up review of the TMB SML OOM plan

Responding to `comments/review_2026-08-24-16-24-27.md`. Both findings are accepted; the plan file (`read-docs-tmb-sml-large-draws-oom-guide-compiled-abelson.md`) has been revised as described below. No code has been changed yet.

## [P1] "One short final chunk" can produce empty chunks for valid pinned chunk counts

**Accepted — the sequential-fill layout is replaced by the review's balanced layout.** The counterexamples are correct: with `Rc = ceiling(R / C)` and sequential filling, `(R, C) = (10, 6)` yields valid counts `2, 2, 2, 2, 2, 0` and `(5, 4)` yields `2, 2, 1, 0`, both passing the `C ≤ R` check. An empty chunk breaks the design twice over: there is no valid draw of its own to duplicate as padding, and `log(Σ_r draw_w) = log(0)` — precisely the value the padding scheme exists to keep off the computation. Silently dropping empty chunks was never on the table, for the reason the review gives: a pinned `tape_chunks` must be honored and the recorded layout must be true.

The plan's chunk-layout section now specifies:

1. `small = floor(R / C)`, `n_large = R %% C`, `large = small + 1`.
2. `n_large` chunks receive `large` valid draws; the remaining `C − n_large` receive `small`. Since `C ≤ R` is enforced at fit time, every chunk has at least one valid draw.
3. The single tape is sized `Rc = ceiling(R / C)`, and **every** chunk smaller than `Rc` — not merely a final one — is padded by duplicating one of its own valid draws under `draw_w = 0`.

The per-chunk valid-count combination formula (`log S_i = logsumexp_c(log S_ic + log Rc_c) − log R`) is unchanged and remains exact. Test (f) now names the regression cases `(10, 6)`, `(5, 4)`, and `C = R`, asserting no empty chunks, chunk weights summing to one, padded duplicates never affecting the result, and equality with the unchunked objective and gradient.

## [P2] Wire the chunked peak slope into default-budget creation, not only family weighting

**Accepted.** The gap identified is real: the previous revision changed the resolver's formula to `chunked_family_weight` but left `max_workload`'s default — produced by `rpbnb_tmb_max_workload()` / `.calibration_default_workload()` from the static `peak_bytes_per_unit` — untouched. A weighted-unit count compared against a unit budget derived from the wrong (smaller) slope under-budgets memory exactly as if the weights had never been fixed.

Plan changes (Phase 3):

- A new **default-budget plumbing** task: the auto-chunk/default unit budget is derived from `chunked_peak_bytes_per_unit` (or the shared conservative constant), and that same constant feeds predicted-peak messages and the memory-detection tests.
- The shared-bound option is tightened per the review: if one common constant set is retained, **both** the bytes-per-unit slope and the family weights are set to component-wise conservative maxima, and static and chunked paths consume that documented common budget.
- A **default-control test** is added — not only explicit-`max_workload` tests — reconstructing predicted bytes from the published chunked constants and verifying they stay within the detected/fallback memory budget.
- The illustrative `C ≈ 8` / `~5.7 GB` figure in the expected-end-state section is now explicitly marked **provisional** (computed with today's static slope) and flagged for recomputation from the published chunked constants before appearing in any docs or messages.

## Disposition

With the balanced `C`-chunk layout eliminating the empty-chunk case and the default unit budget derived from the chunked-graph slope, both items are resolved at the plan level. The layout invariants (no empty chunks, weights sum to one, exactness against the unchunked objective) are pinned by named regression cases. Implementation remains on hold per instruction.
