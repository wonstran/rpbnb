# Response: follow-up review of the TMB SML OOM plan

Responding to `comments/review_2026-08-24-15-54-38.md`. All five findings are accepted; the plan file (`read-docs-tmb-sml-large-draws-oom-guide-compiled-abelson.md`) has been revised as described below. No code has been changed yet.

## [P1] The two-object remainder design under-budgets process peak memory

**Accepted — the two-object design is withdrawn.** The reviewer is right that `TAPE_CALIBRATION$peak_bytes_per_unit` measures the process peak working set while `tape_bytes_per_unit` separately measures the retained tape, so a per-tape check on two simultaneously retained objects ignores object 1's resident tape during object 2's construction/evaluation. The 51/50 example makes the failure concrete: the guard would approve a layout whose combined peak exceeds the budget — exactly the failure this feature exists to prevent.

The plan adopts the review's **preferred option: one max-size object with a padded final chunk.**

- Exactly one `MakeADFun` object of size `Rc = ceiling(R / C)` is ever resident. The short final chunk is padded to `Rc` by duplicating one of its own valid draws, with a new `DATA_VECTOR(draw_w)` (`DATA_UPDATE`, 0/1 per draw) masking the duplicates.
- The per-observation reduction becomes mask-aware: `scaled_sum += draw_w(r) * exp(log_draw(r) − max_log)`, `log S_ic = max_log + log(scaled_sum) − log(Σ_r draw_w(r))`. Because padded rows duplicate a valid draw, the taped running max ranges only over genuinely attainable values — a padded row can tie the maximum but never distort it, and its zero weight drops it from the sum. No `log(0)`/`−Inf` ever reaches the tape, and the requested draw set is preserved exactly.
- The R-side combination uses valid counts: `log S_i = logsumexp_c(log S_ic + log Rc_c) − log R` with `Rc_c` the valid draws per chunk.
- The resolver's post-rounding re-check now verifies the realized single-tape size `ceiling(R/C)` — which, with one resident tape, is the same process-peak quantity the calibration defines. The headline peak formula, the auto-chunk message, and acceptance criterion 2 were all restated in terms of this combined/single-tape quantity.
- The uneven-split test (f) now exercises the padding path, including an assertion that the masked duplicate cannot change `fn`/`gr`.

## [P2] `rpbnb_control()` cannot validate `tape_chunks <= draws`

**Accepted.** A control object is deliberately reusable across estimators and draw counts, so the constructor cannot know `draws`. The plan now has the constructor validate only NULL-or-positive-whole-number; the `tape_chunks ≤ draws` check moves to `.resolve_tape_chunks()` at fit time, where both values exist. Test (k) was updated to assert both halves: constructing a control with a large `tape_chunks` succeeds, and the incompatible **fit call** — not control construction — raises the error.

## [P2] Chunk-1-only `report()` is not a coherent full-objective contract

**Accepted.** The wrapper's methods must all describe the same full-draw objective, and `sum(report(par)$obs_loglik) == -fn(par)` is exactly the invariant a caller will assume. The plan's wrapper contract was rewritten:

- `report(par)` gets **full-draw semantics**: it aggregates the cached per-chunk `obs_loglik` into full per-observation log likelihoods (satisfying the invariant above) and merges parameter-only report entries, which are identical across chunks, taken once. It never returns chunk-local values.
- `env` is a **wrapper-owned environment** holding the documented state (layout, pass-1 cache, best-parameter tracker); the raw TMB object moves to a clearly internal field (e.g. `$chunk_obj`) for diagnostics. Internal code paths that currently reach into `fit$obj$env` will be updated to the wrapper contract rather than being handed the raw environment.
- The "MakeADFun-shaped" label is dropped in favor of "full-objective wrapper with its own state", and test (m) now asserts the `report(par)` invariant and the merged parameter-only entries.

## [P2] The unchunked path cannot be "byte-identical" under unconditional DATA_UPDATE

**Accepted — the review's first option (a genuinely static branch) is adopted, with the second as fallback.** The template gains `DATA_INTEGER(chunked)`: when `chunked == 0` the code takes today's path exactly — no `DATA_UPDATE` registrations, no `w(i)` weighting, no `draw_w` mask — so unchunked fits keep the current tape, memory profile, and calibration. Registration and weighting occur only when `chunked == 1`. The Phase 2 spike explicitly verifies that conditionally registered `DATA_UPDATE` behaves correctly in the shipped TMB version; if it does not, the plan falls back to the review's second option — always-on DATA_UPDATE with the contract downgraded to numerical equivalence, a benchmarked C=1 overhead, and the calibration refreshed to the new baseline.

Test (j) was reworded from "byte-identical" to what is actually assertable: `tape_chunks = 1` takes the `chunked = 0` static branch, produces bitwise-equal `fn`/`gr` values against the current implementation, and registers no dynamic data.
