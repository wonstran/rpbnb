## P2 — the sensitivity experiment was confounded

**Accepted, and demonstrated.** You diagnosed it from the diff; I confirmed it
by running the isolated mutation. Reverting **only** the OPG interval
(`lam_bounds = lam_frozen` dropped from the `bnbr_rp_scores_cpp()` call in
`fit_rpbnb()`), leaving `fit$bounds` correct:

```text
  test-fit-rpbnb.R        pass=44  FAIL=0
  test-cpp-likelihood.R   pass=14  FAIL=0
```

Zero failures. So the three covariance-loop failures I reported came entirely
from the bundled `bounds` change, exactly as you said, and the test exercised
none of the three corrected call sites. Presenting that bundled run as proof was
the substantive error in the last response — a mutation that changes several
things at once cannot attribute a failure to any of them.

Your third sub-point is its own bug and I had not noticed it:
`all(is.finite(fit$se[!is.na(fit$se)]))` is `TRUE` when every SE is `NA`, because
`all(logical(0))` is `TRUE`. Confirmed. The fixture has no fixed parameters, so
the assertion is now `expect_false(anyNA(fit$se))` and
`expect_true(all(is.finite(fit$se)))` directly.

**Replaced with the oracle you recommended.** `rp_vcov_oracle(fit, method,
bounds)` rebuilds the covariance from scratch at `coef(fit)` on the stored
optimization draws under a supplied interval: `solve(crossprod(scores))` for
OPG, `solve(-bnbr_rp_hessian(...))` for analytic, and
`numDeriv::hessian()` of the fixed-bound objective for numeric. The test then
asserts the discriminating pair — `vcov(fit)` matches the oracle under
`fit$bounds`, and differs from it under `fit$bounds_at_optimum`:

```text
  opg       rel(vcov, oracle_FROZEN) = 0.000e+00   rel(vcov, oracle_OPT) = 6.58e-02
  analytic  rel(vcov, oracle_FROZEN) = 0.000e+00   rel(vcov, oracle_OPT) = 4.57e-02
  numeric   rel(vcov, oracle_FROZEN) = 0.000e+00   rel(vcov, oracle_OPT) = 4.57e-02
```

Exact under the frozen interval; 4.6–6.6% away under the other. Nothing about
`bounds`, SE finiteness or `summary()` shape enters that comparison.

**Mutation-tested independently, as you asked.** Each covariance call site
reverted on its own, `fit$bounds` untouched:

```text
  mutate opg       -> test-fit-rpbnb.R  pass=48  FAIL=2
  mutate analytic  -> test-fit-rpbnb.R  pass=48  FAIL=2
  mutate numeric   -> test-fit-rpbnb.R  pass=48  FAIL=2
  restored         -> test-fit-rpbnb.R  pass=50  FAIL=0
```

Two failures each: the "matches the frozen oracle" assertion, and the
"differs from the optimum oracle" discriminator, which also flips because the
mutated fit's covariance *is* the optimum-oracle. That pair is what makes the
test unable to pass for the wrong reason.

## Note — `famoye_lam_from_z()` did not do what its documentation claimed

**Correct.** It was shared by the guard and its tests only; the map was still
written out separately twice in `R/rpbnb_likelihood.R`, once in
`R/rpbnb_hessian.R` and twice in the C++ core. So it prevented guard/test drift
and not drift from the objective, while the documentation claimed the latter.

Rather than weaken the documentation I made the claim true: all three R-side
sites now call `famoye_lam_from_z()`. The C++ core necessarily keeps its own
copy, and the documentation now says so explicitly and points at the R/C++
math-identity assertions in `test-cpp-likelihood.R` as what ties it. Only the
derivative terms (`dlam_dz`, `d2lam_dz2`) remain written out per site, since
they are not this map.
