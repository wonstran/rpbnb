# Response: fourth follow-up review of the TMB SML OOM plan

Responding to `comments/review_2026-08-24-16-31-12.md`. Both findings are accepted; the plan file (`read-docs-tmb-sml-large-draws-oom-guide-compiled-abelson.md`) has been revised as described below. No code has been changed yet.

## [P1] Separate static/chunked calibrations need path-specific budgeting

**Accepted — the plan commits to the shared conservative constant set and drops the separate-constants option.** The review's failure mode is real: with the resolver and the default budget both derived from chunked constants, a family whose *static* graph happened to measure a higher peak slope (or relative weight) could have its `C = 1` static tape approved under the cheaper chunked calibration and run above the advertised limit. The plan had said measurement is authoritative; it cannot then assume the chunked graph dominates for every family and thread mode.

Plan changes:

- Phase 3 now publishes **one calibration**: the bytes-per-unit slope and each per-family/mode weight are the component-wise conservative maxima across the static and chunked graphs. One `max_workload` unit has one meaning on every branch — the resolver's `C = 1` decision, the static tape it selects, and any chunked layout are budgeted in the same currency, so neither branch can be selected above budget because the other graph's calibration was cheaper.
- The documented consequence is stated: unchunked fits are budgeted slightly conservatively wherever the chunked graph's maxima govern. That safety-for-headroom trade is accepted; the path-specific bytes-space alternative (test the `C = 1` candidate under static constants first, then re-resolve chunked) is declined as it would give an explicitly supplied unit-valued `max_workload` two silent meanings.
- The regression fixture the review requests is added: a pinned calibration whose larger component alternates between the static and chunked graphs, proving neither branch can be selected above budget. The default-control test from the previous round now covers safe selection of the static branch as well, since both consume the same constants.
- All resolver/verification text referencing "chunked-graph constants" was rewritten to the shared conservative set (`.resolve_tape_chunks()` formula, expected-end-state formula, acceptance criterion 2).

## [P2] Preserve the documented `max_workload = Inf` opt-out explicitly

**Accepted.** The concern is exact: the new resolver's `floor(max_workload / one_draw_workload)` arithmetic must never run on `Inf` — the current guard short-circuits (`R/tmb_helpers.R:133`), and "Inf disables this guard" is documented user-facing contract. The resolver now has an explicit **step 0**, specified and tested exactly as the review lists:

- `tape_chunks = NULL`, `max_workload = Inf` → `C = 1`, `chunked = 0`, no guard message — today's behavior verbatim.
- User-pinned valid `tape_chunks` with `max_workload = Inf` → the pinned balanced layout is honored with no budget error (chunking on request remains available with the guard disabled).
- The one-draw hard stop is bypassed when the guard is explicitly disabled.

All three cases are added to the workload-guard test list, keeping "Inf disables this guard" true after `.check_tmb_workload()` is replaced.

## Disposition

With the shared conservative calibration as the single budgeting contract and the `Inf` opt-out specified as resolver step 0, both remaining resolver edge cases are closed at the plan level. Implementation remains on hold per instruction.
