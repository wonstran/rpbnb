# Follow-up review: response to the TMB SML OOM plan review

Reviewed `comments/response_2026-08-24-13-46-59.md` against the revised plan and the current calibration/control contracts.

The response substantively accepts all eight original findings (despite saying "all seven"), and the explicit-`report(par)`, integer layout, boundary-refit, exact-draw, runtime-message, benchmark-path, and failure-test revisions address those objections. The new unequal-chunk design introduces one blocking memory issue, plus several plan-contract inconsistencies that should be corrected before implementation.

## Findings

### [P1] The two-object remainder design still under-budgets process peak memory

The revised plan says an uneven split creates two simultaneously retained `MakeADFun` objects, but it continues to claim peak memory is `O(n * max Rc_c)`, chooses `draws_per_chunk_max = floor(max_workload / one_draw_workload)`, and verifies a **per-tape** budget. That is not the quantity `max_workload` currently represents. `TAPE_CALIBRATION$peak_bytes_per_unit` is calibrated against the peak working set for the entire fit/process, while `tape_bytes_per_unit` separately measures memory left resident after construction (`R/tmb_utilities.R:49-66`; `inst/tmb_benchmark_memory.R:18-26`). When object 2 is constructed or evaluated, object 1's tape remains resident.

For example, if the budget admits 60 draws per tape and `R = 101`, an even two-chunk layout has sizes 51 and 50. Both pass the proposed per-tape check, but the process holds both retained tapes while paying the construction/evaluation peak for one of them. The current check can therefore approve a layout whose actual peak exceeds the memory budget—the exact failure this feature is meant to prevent. `parallel_tape = TRUE` makes the transient accounting more important, not less.

Use one of these designs explicitly:

- Prefer one max-size object and pad shorter chunks by duplicating a valid draw plus an updatable zero draw-weight/mask, combining only valid draws. This keeps one tape resident and preserves the requested draw set; ensure invalid padded rows cannot determine the log-sum-exp maximum.
- If two objects are retained, resolve against **combined process peak**, not maximum/per-tape size. The model must include the first object's retained tape plus the second object's construction/evaluation peak (and test both construction orders), with a calibration/benchmark for uneven layouts. The memory regression must exercise this two-object case, and the headline peak formula, predicted-peak message, and acceptance criterion 2 must use the combined quantity.

As written, "both tapes count against the workload budget" in prose is not implemented by the resolver algorithm or the expected-end-state formula.

### [P2] `rpbnb_control()` cannot validate `tape_chunks <= draws`

The plan assigns validation of "positive whole number <= draws" to `R/control.R`, but `rpbnb_control()` and its alias do not receive the fit's `draws` argument. A control object is intentionally reusable across estimators and across fits with different draw counts, so the constructor cannot know this upper bound.

Validate only `NULL` or a positive whole number in the control constructor. Validate `tape_chunks <= draws` in `.resolve_tape_chunks()` (or immediately after `draws` is validated in `fit_rpbnb_tmb()`), where both values are available. Tests should confirm that constructing the reusable control succeeds and that the incompatible fit call—not control construction—raises the error.

### [P2] A chunk-1-only `report()` is not a coherent full-objective wrapper contract

The response calls the stored wrapper `MakeADFun`-shaped, but its `fn()` and `gr()` represent the full requested draw set while `report()` deliberately returns chunk-1-only `obs_loglik`, and `env` exposes only one of two raw-object environments. That makes ordinary-looking operations on the same object disagree about which objective they describe. It is especially misleading because `obs_loglik` is introduced precisely to represent per-observation likelihood contributions, and a caller can reasonably expect `sum(report(par)$obs_loglik) == -fn(par)` up to sign.

Give the wrapper its own environment/state rather than presenting one raw object's environment as the wrapper's, and make `report(par)` return full-draw semantics: aggregate the cached chunk contributions into full per-observation log likelihoods, then merge parameter-only/raw reports whose values are common across chunks. Keep raw chunk objects under clearly named internal fields if diagnostics need them. If chunk-1 reporting is intentionally retained, do not describe the object as MakeADFun-shaped; name the limitation prominently and add a test proving users cannot mistake its `obs_loglik` for the full objective.

### [P2] The unchunked path cannot be “byte-identical” after unconditional dynamic-data changes

The plan says `C == 1` reproduces today's path byte-for-byte and asks for a byte-identical `tape_chunks = 1` test, while Phase 2 unconditionally adds `DATA_UPDATE(Z1/Z2/w)` and multiplies every observation contribution by dynamic `w(i)`. The plan itself notes that the draw transforms now add `Rc * q` tape operations. The tape, memory profile, and execution path therefore cannot be byte-identical to the current implementation even if values and gradients agree exactly when `w = 1`.

Either:

- preserve a genuinely static unchunked branch (for example, a static data flag that avoids `DATA_UPDATE` and weighting when chunking is disabled), then test that branch; or
- change the contract to numerical/backward-compatible equivalence, benchmark the C=1 overhead, and replace "byte-identical" assertions with explicit objective/gradient/message/API checks.

This distinction matters because the plan's calibration is being refreshed specifically to capture tape and peak changes.

### [P3] Align the response and revised-plan bookkeeping

The source review contains eight findings, not seven. The response also says all six acceptance criteria were adopted verbatim, while the revised plan rewrites them and adds two more. Neither affects the design, but correcting the counts will make the review trail auditable and avoid suggesting that one item was skipped.

## Disposition

The original review can be treated as answered once these follow-up items are folded in. The combined-peak issue is blocking because an incorrect guard can still authorize an OOM; the remaining findings are plan/API corrections that are cheapest to settle before code and fixtures are written.
