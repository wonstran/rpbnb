**Scope:** the whole branch as it now stands, deliberately weighted toward areas

## Executive assessment

The branch has converged. The Famoye admissible interval is a single
support-based model property shared by both engines; the optimizer contract on
the RP paths is internally consistent (fixed-bound objective, exact gradient,
post-fit admissibility check that has been shown able to fire); and the
covariance paths are pinned to the objective's own interval by an oracle test
whose sensitivity was established by independent mutation rather than assertion.
The test suite stands at 1,434 passing assertions with the slow TMB tier green.

What remains is not new defects in the reviewed code but three kinds of residue:
an architectural asymmetry between the two Famoye fitters that is currently
resolved in opposite directions without a recorded decision; documentation that
directs users to fields it never documents; and the round-one release-hygiene
items that were explicitly deferred and are still in place. None of these blocks
the branch for research use. The second and third should be closed before any
release; the first needs a decision more than it needs code.

## Findings

### P2 - The two Famoye fitters resolve the moving-bounds trade-off in opposite directions, without a recorded decision

**Locations:** `R/bnb_likelihood.R:1-16` (header contract), `R/bnb_likelihood.R:43-47`,
`R/fit_bnb.R:16-18` (multi-start rationale), `R/fit_rpbnb.R:300-333`;
compare `tests/testthat/test-fit-bnb.R` ("at the optimum the analytic
(frozen-bounds) gradient agrees...").

`fit_rpbnb()` now freezes the admissible interval at the starting values so the
analytic gradient is exactly the derivative of the optimized objective, and
compensates with a post-fit admissibility check. `fit_bnb()`'s Famoye path does
the opposite: `bnb_loglik_vec()` recomputes `lambda_bounds_vec(c1, c2)` from the
current parameters on every evaluation, while `bnb_score_mat()` treats the
bounds as constant. The file header documents this openly, including that the
mismatch reached 3.71 at points away from the optimum, and the multi-start
policy in `fit_bnb.R` exists specifically because the resulting objective is
start-sensitive.

Each choice buys the guarantee the other gives up. Moving bounds make the fitted
lambda admissible **by construction** — `fit_bnb` can never need the escape
warning `fit_rpbnb` now carries — at the price of search directions that are not
derivatives of the evaluated function en route. Frozen bounds give exact
gradients at the price of possible escape, now detected but not prevented. Both
are defensible; holding both at once in one package, on two functions that
`?rpbnb` presents as two engines for the same family, is a decision that
currently exists only as an accident of history.

This is not a request to change either fitter. It is a request to record the
decision: a short paragraph in each file (and ideally in the `rpbnb()` man page's
engine matrix) saying which horn each path takes and why, cross-referencing the
other. There is also one concrete consistency check worth adding while doing so:
`fit_bnb`'s converged point is a fixed point of the frozen-gradient system
(gradient uses bounds evaluated at the same point), so its Hessian/SE paths at
`bnds_hat` (`fit_bnb.R:127`) are consistent at the optimum — that argument is
currently implicit in the header note and deserves to be stated where the SEs
are computed, since it is the reason the documented ~1e-3 agreement is
acceptable there and only there.

### P3 - The TMB fitter's warning directs users to fields its documentation does not contain

**Locations:** `R/fit_rpbnb_tmb.R:91-102` (`@return`, `lambda_bounds` paragraph),
`R/fit_rpbnb_tmb.R:642-643` (warning text), `R/fit_rpbnb_tmb.R:729-730`
(fields on the returned object).

The `@return` block for `fit_rpbnb_tmb()` enumerates the fit's diagnostic fields
in detail (`optimizer`, `method`, `boundary_report`, `boundary_sides`,
`lambda_bounds`) and states of the bounds that "they are *not* recomputed at the
optimum." Since `a6f2d87` that sentence is misleading: the fitter recomputes the
interval at the optimum for the admissibility check and stores it as
`lambda_bounds_at_optimum` alongside `lambda_admissible` — and the warning text
explicitly tells the user to "See fit$lambda_admissible and
fit$lambda_bounds_at_optimum," neither of which appears anywhere in the help.
A user following the warning into `?fit_rpbnb_tmb` finds a document that appears
to deny the fields exist.

Amend the `lambda_bounds` paragraph: the bounds used by the likelihood are
frozen at the starting values; the interval admissible at the optimum is
recomputed for validation only and stored as `lambda_bounds_at_optimum`, with
`lambda_admissible` recording the comparison. The same two fields (plus
`bounds_at_optimum` on `rpbnb_fit`) are documented today only in internal
constructor comments; `fit_rpbnb()`'s `@return` is a one-liner so the omission
is milder there, but its warning text has the same forward reference and a
sentence in its `@return` would close it. Doc regeneration is idempotent, so
this is a source edit plus one `roxygenise()`.

### P3 - LR and boundary tests inherit the frozen-interval caveat for bounded random-coefficient distributions

**Locations:** `R/boundary_tests.R` (restricted refits via `.fixed`/`.opt_draws`),
`R/lr_test.R`, `R/fit_rpbnb.R:300-333`.

`rpbnb_boundary_tests()` compares a full fit against restricted refits, each fit
maximizing an objective whose lambda range is frozen at that fit's own starting
values. For normal (and lognormal, both-margins) coefficients this is moot: the
support bound is the constant `[-1, 1]`, both objectives use the same map, and
common random numbers do the rest. For uniform/triangular coefficients — where
the bound moves with `beta`, `m`, `s` — the full and restricted objectives are
maximized over intervals frozen at different points, and the LR statistic
compares maxima over (slightly) different lambda ranges. The effect is
second-order and bounded by the same frozen-bounds caveat already listed as open
item 2, but nothing in `?rpbnb_boundary_tests` or `?lr_test` says so, and the
boundary-test machinery predates the support-bound work, so no round ever looked
at the interaction. A sentence in each help page confining the caveat to bounded
distributions is sufficient; no code change is warranted ahead of the
parameter-dependent-constraint work already on the open list.

## What is working well

- One support-based admissible interval, shared across both engines and all
  covariance paths, with the derivation, the floor-only asymmetry, and the
  measured counterexamples documented at the definition site rather than in
  commit messages alone.
- The verification culture the review rounds forced is now embedded in the
  tests themselves: the guard's arithmetic is pinned through production code,
  premises (intervals differ; bound is parameter-dependent) are asserted rather
  than assumed, the covariance test carries its own oracle and discriminating
  pair, and sensitivity was established by independent mutation.
- The engine boundary is honest: `rpbnb()` rejects wrong-engine arguments by
  name, the Gaussian thread cap makes the known SIGSEGV unreachable with the
  request/realization recorded on the fit, and the TMB engine refuses offsets
  rather than dropping them.
- Cross-engine agreement is tested where it is meaningful (bounds identical and
  draw-independent; logLik within measured tolerance) and deliberately not
  where it is not (separate Halton generators guarded by an equivalence test).
- The bit-identity baseline survived eight rounds of surgery with exactly one
  re-capture, disclosed, explained, and accompanied by a separately pinned
  bound so tape and bound changes stay distinguishable.

## Remaining status

The three known open numerical items are unchanged and correctly documented in
NEWS: the Gaussian atomic is not thread-safe (public cap only); the Famoye
interval is frozen at the starting values on both engines, with escape detected
and warned but not prevented where the bound is parameter-dependent; and
Gaussian tail cells whose NB2 CDF endpoints both reach the `safe_qnorm()` clamp
collapse to the `1e-300` floor. The findings above add no new numerical defects
— the branch's remaining work is one architecture decision to record, a small
set of documentation amendments, and the deferred hygiene items that stand
between a green test suite and a green `R CMD check`.
