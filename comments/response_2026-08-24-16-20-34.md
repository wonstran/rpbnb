# Response: second follow-up review of the TMB SML OOM plan

Responding to `comments/review_2026-08-24-16-15-25.md`. All three findings are accepted; the plan file (`read-docs-tmb-sml-large-draws-oom-guide-compiled-abelson.md`) has been revised as described below. No code has been changed yet.

## [P1] The `n × C` pass-1 cache can exceed the memory budget

**Accepted — the plan adopts the streaming design.** The counterexample is decisive: tape size and cache size move in opposite directions as chunks shrink, and at n = 500,000, R = 5,000 the auto-resolver could legitimately pick `Rc = 1`, `C = 5,000` (the one-draw tape passes the hard stop) while the wrapper silently allocates a ~20 GB `n × C` matrix the guard never models. An OOM guard that itself allocates the OOM is not acceptable.

The wrapper contract now states **wrapper state is O(n), never O(n × C)**:

- `fn(par)` streams across chunks, folding each chunk's `obs_loglik` into a per-observation **online log-sum-exp accumulator** (running max plus rescaled sum, both n-vectors). No chunk column is retained; the cache keeps only `par`, the final n-vector `logS_i`, and the objective value.
- `gr(par)` uses the cached full denominator `logS_i` and **re-runs `report(par)` per chunk** to recover that chunk's `logS_ic` before its weighted `obj$gr(par)` call, computing `w_ic = Rc_c · exp(logS_ic − logS_i − log R)` stably in log space.
- The cost is one additional serial report sweep when both `fn` and `gr` are requested; this sweep is explicitly included in the Phase 3 wall-time benchmark (neither report pass is amortized by OpenMP).
- The wrapper's `report(par)` full-draw semantics are unaffected — `logS_i` is exactly the full per-observation log likelihood, so the `sum(report(par)$obs_loglik) == -fn(par)` invariant is preserved without any per-chunk retention.
- The resolver's re-check note, the headline peak formula (now `... × n × ceiling(R/C) + O(n)` wrapper vectors), acceptance criterion 2, and the RDS/cache tests were updated accordingly.

The bounded hybrid cache alternative is declined for now: it buys back one report sweep at the price of a second budgeted allocation the resolver must track and a mode switch to test. If the Phase 3 benchmark shows the extra sweep is a real bottleneck, the hybrid can be revisited as a measured optimization with its bytes explicitly reserved by the resolver, as the review prescribes.

## [P1] The workload constant is calibrated on the static graph, not the chunked graph

**Accepted.** The point is correct and subtle: the `chunked = 0` static branch preserves the old tape precisely so that existing fits are untouched — but that same separation means `peak_bytes_per_unit` measured on the static graph is evidence about a graph the auto-chunk guard never runs. The `chunked = 1` graph adds the `draw_w(r) * exp(...)` mask multiplication inside every observation-draw reduction (O(n × Rc) tape nodes) plus dynamic Z and per-observation `w`, so its peak slope must be presumed different until measured.

Plan changes:

- Phase 3 gains an explicit **chunked-mode memory calibration**: the benchmark builds the `chunked = 1` mask-aware objective for every family, covering padded and all-valid masks and the supported thread/`parallel_tape` modes.
- The resolver consumes chunked-graph constants: either a published separate `chunked_peak_bytes_per_unit`/family-weight set, or — if the measurements demonstrate one shared upper bound covers both graphs — a shared constant set to the **larger** slope. `.resolve_tape_chunks()`'s workload formula now names `chunked_family_weight` rather than reusing the static constants.
- The memory regression test **feeds the actual guard constants** rather than remaining an informational C=4 slope comparison.
- The claim that `n × Rc` maps to the same calibrated process peak as the static tape has been removed from the resolver text, the expected-end-state formula, and acceptance criterion 2; all three now reference the chunked-graph calibration.

## [P2] "Bitwise equal to current code" conflicts with Phase 1's algebraic rewrites

**Accepted.** As written, test (j) demanded that the Phase 2 static branch be bitwise-equal to the pre-Phase-1 implementation, which Phase 1's `dnbinom2`/`dpois` replacement and term hoisting make impossible — those rewrites are algebraically exact but reorder floating-point operations, which is why the Phase 0 fixture contract already allows ~1e-12.

Test (j) is redefined as **phase-attributable checkpoints**:

1. Phase 1 vs the original current code: agreement at the algebraic-equivalence tolerance (~1e-12), per the existing fixture contract.
2. A captured **post-Phase-1 static baseline**; Phase 2 with `chunked = 0` must match *that* baseline — bitwise if the spike demonstrates it, otherwise at the established tolerance — and must register no dynamic data.

A failure now points at the phase that caused it, and no combined-phase assertion demands the impossible.

## Disposition

With streaming O(n) wrapper memory, chunked-graph guard constants, and phase-scoped equivalence checkpoints folded in, both blocking P1 items are resolved at the plan level: every allocation the design makes — tape, mask, and wrapper state — is now either measured by the guard's calibration or bounded O(n) by construction. Implementation remains on hold per instruction.
