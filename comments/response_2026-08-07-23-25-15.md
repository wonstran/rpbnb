## P0 — Gaussian/OpenMP segfault was not blocked

**Accepted in full.** The criticism is exactly right: I diagnosed this during
the merge, proved it predates the merge, wrote it up in the README and in a
test comment, and then left `control$n_cores` flowing to `MakeADFun()` for
every family. Documentation is not a guard against process termination, and a
user who loses a session to `n_cores = 2L` is not helped by a README section.

`fit_rpbnb_tmb()` now caps the Gaussian family at one thread before any TMB
object is constructed (`R/fit_rpbnb_tmb.R`). `parallel_tape` is forced off on
the same path, because `.make_rpbnb_tmb_object()` re-applies the TMB thread
configuration and would otherwise re-enable concurrent taping for the family
that cannot tolerate it. The cap warns, and `fit$parallel` retains both
`requested` and `realized` so the difference is visible on the object rather
than only in a console message.

Verified: a Gaussian fit requesting `n_cores = 4L` warns, returns
`realized = 1L`, `requested = 4L`, and the process survives.

On the test shape you asked for: I did **not** add a subprocess that attempts
the crashing call. Two new in-process tests in `tests/testthat/test-parallel.R`
assert the cap (Gaussian is capped and warns) and its converse (Frank at
`n_cores = 2L` is *not* capped, so the guard cannot silently serialize
everything). Asserting the cap is the property that must hold; spawning a
subprocess to confirm the crash still crashes would re-verify a defect already
reproduced in unmodified `rpbnb.tmb` 0.3.5 and would add a
platform-and-timing-dependent test for no additional safety. If you want the
crash itself pinned so that fixing it fails loudly, say so and I will add a
`callr`-style subprocess test gated behind `RPBNB_RUN_SLOW`.

The underlying atomic is still not thread-safe. That is tracked separately.

## P0 — Frozen Famoye bounds can admit a negative joint PMF

**Confirmed; partially fixed.** Your counterexample reproduces exactly against
the package's own `lambda_bounds_vec()`:

```text
frozen  bounds (mu = 1,   m = 0.5): [-2.999875,  4.098108]
current bounds (mu = 0.1, m = 0.5): [-1.132545, 17.637867]
lambda = -2 inside frozen box?  TRUE
lambda = -2 inside current box? FALSE
dependence factor at observed (0,0):  0.992719   (no penalty)
upper-tail limit 1 + lambda*c1*c2:   -0.765934   (negative pmf)
```

Your analysis of why the `1e10` penalty cannot help is also right: it is flat
on each side, so it contributes no gradient that could steer the optimizer
back into the valid region.

What I changed: the bound computation is factored into `.lambda_bounds_at(par)`
and evaluated a second time at the fitted parameter vector. When the fitted
lambda falls outside the interval admissible at the optimum, `fit_rpbnb_tmb()`
raises a warning that names both intervals and states plainly that the joint
pmf is negative in the count tails and the fit should not be interpreted. Two
new fields, `lambda_bounds_at_optimum` and `lambda_admissible`, carry the
result on the object so a script can branch on it.

What I did **not** change, and why: this is precisely the "at minimum" remedy
you described, and it inherits the limitation you attached to it — it catches
invalid results, it does not repair the optimized objective. The real fix is to
make the constraint a function of the current parameters across the current
draws, which means moving the bound computation inside the template. The bounds
arrive as `DATA_SCALAR(lamLo)`/`DATA_SCALAR(lamHi)`; making them
parameter-dependent puts a max/min over an n-by-draws grid of `c_val()` on the
AD tape, inside the objective, with the resulting non-smoothness in the
gradient. That is a redesign of the Famoye path with real consequences for tape
size and optimizer behaviour, not an edit — and it needs its own validation
against the existing Famoye tests and the SML bit-identity baseline. I was not
willing to attempt it as part of a review-response pass and present the result
as verified.

Until that lands, a Famoye fit that trips this warning should be treated as
invalid, and the practical remedy is the one the warning states: refit from
starting values nearer the optimum so the frozen box is tighter.

## P1 — Gaussian tail intervals collapse at the quantile clamp

**Confirmed; deferred.** Your count matches the figure the template itself
records: `src/rpbnb_tmb.cpp` documents "245 of the 3,487 truck cells at the
starting values", and names the same cause (both CDF endpoints reaching the
`safe_qnorm()` clamp, so the integration interval has zero width) and the same
remedy you propose (a separately accumulated survival function, because once
the NB2 CDF saturates the cell cannot be recovered from the CDF at all).

So this is a known, in-source-documented limitation rather than a discovered
defect — but your framing is the more honest one, and I agree with it: a
documented approximation that silently replaces ~7% of cells on a real fixture
with a flat floor worth ~169,000 nats is load-bearing, not incidental, and the
existing test asserting only "less wrong than the previous four-corner form"
does not constrain it.

I have not attempted this. Carrying survival/log-survival out of
`nb2_cdf_pair()` and rebuilding the Gaussian rectangle from marginal masses is
numerical work of the same order as the original `gaussian_cell_prob()`
implementation, and it must not disturb the Frank and Clayton paths that
currently share that helper. Doing it properly needs the reference comparison
you describe — independent per-cell values for the currently collapsed cells —
built first, so that the change can be shown to fix them rather than merely to
move the number. That is the right next piece of work on this engine and it
should not be rushed into a response pass.

Nothing about the current behaviour has changed. It remains the case that
Gaussian-copula fits on heavy-tailed data lose those cells' likelihood
contribution.

## P1 — Tier runner false green, and tests depending on ignored data

**Accepted in full; both halves fixed.**

On the runner: you are right about the mechanism and about the contract being
false. `as.data.frame()` on a testthat result puts expectation failures in
numeric `failed` and test-level errors in logical `error`; `tools/test-tiers.R`
summed only the former and set exit status from it. `run_files()` now
accumulates `error` alongside `failed`, `report()` prints an `err=` column, and
exit status is driven by the sum of both. Confirmed by inspection that the
`error` column exists and was previously unread.

On the data: this one is mine, and it is a merge regression rather than
inherited. I gitignored `inst/extdata/export_dense_all.csv` during the merge —
deliberately, since it is 9.96 MB of local research data and its sibling
`export_open_all.csv` was already ignored on the same grounds — without
checking what depended on it. Three tests in `test-fit-copula.R` then referenced
it with `mustWork = TRUE`, which errors rather than skips, and `NOT_CRAN=true`
meant their `skip_on_cran()` guards did not fire. Combined with the runner
defect, a clean checkout errored and reported success.

Those call sites now use a `dense_truck_fixture()` helper in
`tests/testthat/helper-slow.R` that skips with an explicit reason when the file
is absent. I chose skipping over your first suggestion (track a reduced
redistributable fixture) because the assertions are calibrated against specific
cell counts on that specific dataset — the 245-collapsed-cell threshold and the
196,000–203,000 nat separation both depend on it — so a reduced fixture would
need those thresholds re-derived, which is work that belongs with the Gaussian
tail fix above rather than ahead of it. Skipping is honest in the meantime; the
tests no longer error, no longer silently pass, and now say why they did not
run.

## P1 — Invalid significance tests on random-effect scales

**Accepted in full; fixed.** Your reading is correct on both counts, and the
precedent you cite is exact: `.print_natural_scale_footnote()` in `R/methods.R`
sets `z`/`p` to `NA` for positive scale and dispersion parameters and prints a
note that their null is a boundary, directing users to `lr_test()`. The TMB
engine's `summary()` reintroduced the Wald test the Rcpp engine had removed.

`summary.rpbnb_tmb_fit()` no longer computes p-values or significance stars for
`log_sd*`/`log_s*`/`log_w*` rows. Both scales are now labelled explicitly —
`Estimate (log)`, `Std. Error (log)`, `Estimate`, `Std. Error` — and the
natural-scale standard error is the delta-method transform
`scale * SE(log_scale)` rather than the log-scale SE printed beside a
natural-scale estimate. The same boundary note as the Rcpp engine is printed
below the block.

This was worth catching for a reason beyond the specific rows: it is the
failure mode a two-engine package invites, where a decision reached and
documented for one engine is silently unwound by the other. The comment at the
fix cross-references the Rcpp implementation so the two stay tied.

## P2 — Control validation gaps

**Accepted; fixed.** All five cases you list were accepted before the change
and are rejected now: `reltol = -1`, `print_level = NA`, `halton_burn = -1`,
`iterlim = -5`, `iterlim = "many"`. `iterlim`, `print_level` and `halton_burn`
are validated as whole numbers with appropriate minima and an upper bound
before integer coercion; `reltol` must be one positive finite number.

The `halton_burn = -1` consequence you identified is the one that mattered:
`.tmb_halton_uniform()` slices `(burn + 1):(burn + n_draws)`, so a negative
burn returned 9 rows for 10 requested draws and the likelihood was averaged
over a grid of the wrong size, silently.

`fit_rpbnb_tmb()` now also checks that `control` inherits from
`rpbnb_tmb_control`, as you recommended. Your reasoning about direct calls
bypassing the wrapper is right, and the failure it prevents is unpleasant:
passing an `rpbnb_control()` makes `control$gradtol` read as `NULL`, which
turns the restart loop's comparison into `logical(0)`.

## What is still open

1. The Gaussian atomic is not thread-safe. The cap makes it unreachable; it
   does not fix it.
2. The Famoye constraint is still frozen at the starting values. Invalid
   optima are now detected and reported, not prevented.
3. Gaussian tail cells still collapse to the probability floor.

Items 2 and 3 are model-validity limitations of the TMB engine, not of the
merge, and both need dedicated numerical work with references built first. I
would not describe the TMB engine as generally trustworthy for Famoye fits that
move far from their starting values, or for Gaussian-copula fits on
heavy-tailed counts, until they are done.
