# Third follow-up review: TMB SML OOM plan response

Reviewed `comments/response_2026-08-24-16-20-34.md` against the latest revised plan.

The response resolves the prior three findings: streaming keeps wrapper state O(n), the proposed benchmark now measures the chunked graph used by the guard, and the equivalence checkpoints are phase-attributable. One layout correctness issue remains, plus one calibration-plumbing detail that should be explicit before implementation.

## Findings

### [P1] “One short final chunk” can produce empty chunks for valid pinned chunk counts

The plan defines one tape of size `Rc = ceiling(R / C)` and describes sequential full chunks followed by one padded short final chunk. That layout does not always yield exactly `C` nonempty chunks. For example:

- `R = 10`, `C = 6`, `Rc = 2` gives sequential valid counts `2, 2, 2, 2, 2, 0`.
- `R = 5`, `C = 4`, `Rc = 2` gives `2, 2, 1, 0`.

Both controls are valid under the proposed `C <= R` check. The final empty chunk has no valid draw to duplicate, `sum(draw_w) = 0`, and the mask-aware likelihood takes `log(0)`, contradicting the design's no-zero guarantee. Silently dropping empty chunks would also mean a user-pinned `tape_chunks` value is not honored and the recorded layout/message is wrong.

Build an explicitly balanced `C`-chunk layout instead:

1. `small = floor(R / C)`, `n_large = R %% C`, `large = small + 1` when needed.
2. Assign `n_large` chunks `large` valid draws and the remaining chunks `small` valid draws. Because `C <= R`, every chunk has at least one valid draw.
3. Tape at `Rc = ceiling(R / C)` and pad **every** smaller chunk—not merely a final chunk—by duplicating one of that chunk's own valid draws with zero `draw_w`.

The existing per-chunk valid-count formula then remains exact. Add regression cases for `(R, C) = (10, 6)`, `(5, 4)`, and `C = R`, asserting no empty chunks, weights summing to one, and equality with the unchunked objective/gradient.

### [P2] Wire the chunked peak slope into default-budget creation, not only family weighting

The response says the resolver consumes chunked-graph constants, but the plan's resolver formula explicitly changes only `family_weight`. `max_workload` is still a weighted-unit count, and its default is currently created by `rpbnb_tmb_max_workload()` / `.calibration_default_workload()` from `peak_bytes_per_unit`. If the new chunked graph has a larger bytes-per-unit slope and the default remains derived from the static slope, comparing `n * chunked_family_weight` to that old unit budget still under-budgets memory.

Make the plumbing explicit in Phase 3:

- When separate constants are retained, derive the auto-chunk/default unit budget from `chunked_peak_bytes_per_unit`, and use the same constant in predicted-peak messages and memory-detection tests.
- If one shared upper bound is chosen, set both the slope and family weights to the component-wise conservative maxima and have static and chunked paths consume that documented common budget.
- Add a default-control test (not only an explicit `max_workload` test) that reconstructs predicted bytes from the published chunked constants and stays within the detected/fallback memory budget.

The illustrative `C ≈ 8` / `5.7 GB` example should be recomputed after this calibration or clearly marked provisional until those constants exist.

## Disposition

The streaming padded-single-tape approach remains viable. The empty-chunk case is blocking because it makes valid `tape_chunks` inputs produce an undefined likelihood; the calibration item is a guard-integration clarification needed to preserve the advertised memory bound.
