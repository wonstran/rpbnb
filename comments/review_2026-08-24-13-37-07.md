# Review: TMB SML large-draw OOM plan

Reviewed `C:\Users\zwang9\.claude\plans\read-docs-tmb-sml-large-draws-oom-guide-compiled-abelson.md` against the current TMB fitter, inference path, boundary-refit path, workload guard, and tests.

The chunk-gradient identity is sound for a fixed draw set, and reusing one chunk-sized tape is a promising design. The plan needs the following corrections before implementation.

## Findings

### [P1] Pass the requested parameter vector explicitly to `obj$report()`

Phase 2 says pass 1 should set each chunk and call `obj$report()` to obtain `obs_loglik`. TMB's `report` function defaults to its internal `last.par`, not to the wrapper's `par` argument. TMB also explicitly warns callers not to rely on defaults for `fn`, `gr`, `he`, or `report`. A new wrapper `fn(par)` may not have called the raw `obj$fn(par)` at all, so `last.par` can be stale or unset. The reported chunk likelihoods, objective, and softmax weights can therefore be evaluated at the wrong parameters even while `obj$gr(par)` uses the requested parameters.

Call `obj$report(par)` for every chunk and add a regression test that deliberately leaves `obj$env$last.par` at a different vector before invoking the wrapper. This is required for correctness, not just cache efficiency. The relevant upstream implementation is `report <- function(par = last.par) ...` in [TMB's `MakeADFun` source](https://github.com/kaskr/adcomp/blob/master/TMB/R/TMB.R).

### [P1] `ceiling(weighted_workload / max_workload)` does not always produce a safe integer chunk size

The proposed auto rule computes `C` from the continuous workload ratio, then uses `Rc = ceiling(draws / C)` by rounding the total draws up. Integer rounding can put the selected chunk back over budget. For example, with per-draw weighted workload 1, `draws = 10`, and `max_workload = 3.9`, the rule selects `C = ceiling(10 / 3.9) = 3`; the actual chunk size is `ceiling(10 / 3) = 4`, whose workload is 4 and exceeds the budget.

Resolve from the maximum safe integer draws per tape instead: compute the one-draw workload, stop if it exceeds the budget, derive `draws_per_chunk_max = floor(max_workload / one_draw_workload)`, and choose/verify a chunk count whose actual `ceiling(draws / C)` is no greater than that value. In all cases, re-check the realized per-chunk workload after rounding. Tests should cover just-below-boundary fractional budgets and `parallel_tape = TRUE`.

### [P1] Boundary refits will discard chunking and can recreate the original OOM

The plan wires chunking only into `fit_rpbnb_tmb()`. Current `rpbnb_tmb_boundary_tests()` reconstructs each restricted model from `fit$draws` and, when no control is supplied, creates a control with `max_workload = Inf` (`R/tmb_boundary_tests.R:203-215`). The `rpbnb()` front end calls it without forwarding the main fit's control (`R/rpbnb.R:395-403`). Thus an auto-chunked large fit can immediately be refit as one full tape for every requested LR test, defeating the fix and risking OOM. The same issue applies to the Laplace-to-SML fallback refits.

Persist enough resolved state on the fit to reconstruct the integration rule and memory policy (`draws_requested`, `draws_effective`, resolved `tape_chunks`, and the relevant workload/thread policy), and explicitly propagate it through boundary refits. If `boundary_draws` changes, resolve a safe chunk layout for that draw count rather than blindly reusing either the old count or `Inf`. Add an end-to-end test through `rpbnb(..., boundary_tests = TRUE)` as well as a direct `rpbnb_tmb_boundary_tests()` test.

### [P2] Rounding draws up changes the SML estimator, so the advertised exactness is too broad

The identity in "Why chunking is exact" is exact for the same `R` draws. Phase 2 instead changes a request from `R` to `C * ceiling(R / C)` whenever `R` is not divisible by `C`; those additional Halton points change the simulated likelihood, coefficients, and standard errors. The chunked result is exact for `draws_effective`, but it is not equivalent to today's unchunked fit at the user-requested `draws`.

Prefer preserving the exact requested draw set, for example by supporting a shorter final chunk with a validity mask/draw weights and combining chunk sums with their actual draw counts. If rounding is retained, make it an explicit API contract: store requested and effective counts separately, message the change, ensure `fit$draws` semantics are unambiguous for existing boundary-test code, and compare chunked results against an unchunked `draws_effective` reference. Also define what happens when a user pins `tape_chunks > draws`; silently increasing a one-draw fit to many draws is surprising.

### [P2] Define the complete `fit$obj` compatibility contract for the wrapper

The proposed wrapper is described as returning `fn`, `gr`, and a best-parameter tracker, then replacing the raw TMB object under `keep = "full"`. Existing code and tests treat `fit$obj` as a `MakeADFun`-like object with at least `par`, `fn`, `gr`, `he`, `report`, and `env`; some tests evaluate `fit$obj$fn()`/`gr()`/`he()`, and the saved-object tests rely on a dead external pointer being retaped after `saveRDS()`/`readRDS()`. Only guarding `TMB::tmbprofile()` leaves the rest of that contract unspecified.

Specify which fields are forwarded, reimplemented, or deliberately unavailable. In particular, the stored wrapper should expose the full-draw `fn`/`gr`, an explicit `par`, coherent reporting behavior, and deterministic error behavior for unsupported `he`/TMB-only operations. Add tests for `keep = "full"`, direct post-fit evaluation at a non-optimal parameter vector, and an RDS round trip. Restore or deterministically set `Z1`, `Z2`, and `w` on every exit path so the serialized raw object is not dependent on which chunk happened to run last.

### [P2] Benchmark the report pass under threaded fits before promising “~2x” cost

`REPORT()` is emitted only by TMB's ordinary double-mode execution, not its parallel tape regions. The extra pass that obtains all per-observation chunk contributions is therefore not automatically comparable to the multithreaded gradient sweep. For `n_cores > 1`, a serial `C`-chunk report pass plus parallel gradient sweeps may cost materially more than the plan's “~1.5–2x” estimate.

Benchmark wall time at one thread and representative multi-thread settings for each family before putting a numeric multiplier in the auto-chunk message. Until measured, describe the cost qualitatively. The spike should verify values and thread behavior, not only that a vector is returned.

### [P3] Use one real benchmark script path and repair the existing stale self-references

The plan alternates between `inst/benchmark_memory.R` and `inst/tmb_benchmark_memory.R`. Only `inst/tmb_benchmark_memory.R` exists, although that file and several current comments still contain the stale shorter path. Since Phase 3 refreshes `TAPE_CALIBRATION$source`, the raw CSV, README text, and drift tests, it should explicitly standardize all of these references on the actual filename rather than perpetuate two names.

### [P3] Complete the distribution and failure-path test matrix

The fixture matrix names normal, lognormal, and uniform coefficients but omits the registered triangular distribution. Add it to at least one chunk-equivalence case. Also test error cleanup during a middle chunk, non-finite chunk log likelihoods/weights, `tape_chunks = 1`, `tape_chunks > draws`, no-random-coefficient SML (where effective draws are currently forced to one), and both requested/effective draw metadata. These cases exercise wrapper state and API semantics that fixed-parameter equivalence tests will not catch.

## Suggested acceptance criteria

1. For a draw count preserved exactly, chunked `fn`, `gr`, and finite-difference Hessian agree with the unchunked objective at multiple non-optimal parameter vectors, with raw `last.par` deliberately stale.
2. Every resolved layout is re-checked to satisfy the per-tape workload budget after integer rounding.
3. Automatic and direct boundary-test refits retain a safe chunk policy and the intended common random numbers.
4. A full retained chunked object remains usable after `saveRDS()`/`readRDS()` for the operations the package documents as supported.
5. Memory verification compares slopes or subtracts the fixed process baseline; absolute peak RSS should not be asserted to be exactly one quarter at `C = 4`.
6. Runtime messaging is based on measurements at both one and multiple threads.
