## P0 — Finite SML draws are not the support of the model

**Accepted. My previous reasoning was wrong.**

I claimed the finite-draw bound was "the correct notion" for SML because "the
SML likelihood genuinely is an average over those draws, so the joint pmf only
has to be non-negative at each of them." That is exactly the confusion you name:
it treats a quadrature rule as if it defined the model. The mixing distributions
stay continuous under both estimators, the package's own `?fit_rpbnb_tmb` says
SML and Laplace are "different approximations to the same integral", and nothing
about choosing 50 nodes instead of 400 redefines which parameter values give a
valid probability model.

The decisive check, which I had not run and should have: **the finite-draw bound
is monotone in the draw count.**

```text
      5 draws -> [ -2.55029,   3.13131]
     50 draws -> [ -2.20404,   2.91935]
    400 draws -> [ -2.14217,   2.75276]
   5000 draws -> [ -2.04561,   2.34654]
  50000 draws -> [ -1.91394,   2.26066]
  support      -> [-1, 1]
```

The "admissible set" I was defending shrinks toward the support bound as the
approximation improves. A constraint set that is a function of `R` is not a
parameter space, and your point about the missed neighbourhoods is the substance:
they carry positive probability under the stated mixing distribution, so a lambda
the draws happen not to expose still makes the model's conditional pmf negative
on a set of positive measure.

There was no defensible second option. Your alternative — redefine SML as
fitting a draw-dependent discrete mixing distribution — contradicts the API, the
simulator, and the "same integral" contract, as you say.

**What changed.** `.lambda_bounds_at()` (Halton) and `.lambda_bounds_latent()`
are both gone, replaced by one `.lambda_bounds_support()` used for both
estimators and for both the frozen bounds handed to the template and the post-fit
re-check. Per observation and margin it builds the attainable `eta` interval from
the fixed part plus the sum of the per-column deviation supports, applies the
template's own clamps, maps through `mu = exp(eta)` and the decreasing
`c = (1 + d*m*mu)^(-1/m)`, and evaluates the corners of the resulting
`c`-rectangle. The corner enumeration is exact for the reason given last time
(pointwise maxima of bilinear functions attain their suprema at vertices).

**On your instruction to propagate the bounded supports rather than assume
`(0,1)`** — done, and you were right that this matters beyond tidiness. I had
described `(0,1)` as "conservative", which is true for lognormal but *false* for
uniform and triangular: their deviation support is `(-s, s)`, genuinely bounded,
so forcing `(0,1)` would be **over-strict** and would reject admissible fits.
The four supports now used, read off `rand_dist_registry`'s `dev`:

```text
  normal      dev = s*base,                   base unbounded -> (-Inf, Inf)
  triangular  dev = s*base,                   base in (-1,1) -> (-s, s)
  uniform     dev = s*(2*base - 1),           base in (0,1)  -> (-s, s)
  lognormal   dev = sign*exp(b + s*base) - b, base unbounded ->
                (-b, Inf) for sign = +1, (-Inf, -b) for sign = -1
```

Verified: with normal coefficients loaded in both margins, SML at 5 draws, SML at
400 draws and Laplace all return exactly `[-1, 1]`; a uniform coefficient returns
`[-2.4533, 3.0375]`, wider than `[-1, 1]`, as its bounded support requires.

**A consequence I want to flag rather than bury: this moved the SML bit-identity
baseline.** `BASELINE_SML_LOGLIK` went from `-949.6478422037` to
`-949.6478374514`, a shift of 4.75e-06 nats, because `lamLo`/`lamHi` are inputs
to the tape and `z_dep` maps through them. On that fixture the bound went from a
grid box to `[-1.732, 1.732]` and the fitted `lam` is 0.43, nowhere near either
end, which is why the shift is microscopic rather than structural.

Re-pinning a bit-identity baseline is the thing that test's own comment warns
against, so I did not do it quietly:

- The value is re-captured once, with the old value, the delta and the cause
  recorded in the file.
- `lambda_bounds` is now pinned **separately** in the same test. That preserves
  what the guard measures and sharpens it: a tape regression moves the
  log-likelihood while leaving the bounds alone, a deliberate bound change moves
  both, so the two are distinguishable in a way they were not before.
- The existing warning in that file is about absorbing an *optimizer-schedule*
  change, which would destroy the guard. This is a change to the tape's input
  data, and the tape structure is unchanged.

If you would rather the baseline were left at the old value and the test marked
failing pending review, say so — but I think re-capturing with the bound pinned
alongside is the stronger arrangement, and I did not want to hide that a
bit-identity constant moved.

Two of the tests I added in `8d48f20` asserted the now-false claim that the SML
bound is strictly wider than the Laplace one. They are rewritten to assert what
should actually hold: the SML bound does not move with the draw count and equals
the Laplace bound.

## P1 — R underflow drops a random effect the template keeps positive

**Accepted; fixed.** Reproduced exactly: `exp(-1000)` is `0` in R while the
template clamps `log_sd` to `-20` and keeps `exp(-20) = 2.061154e-09`. The helper
read `s > 0` as "does this margin vary", so it declared both margins fixed and
returned `[-2.999874779, 4.098107520]` — and, as you note, a dropped effect
*widens* the interval, so `lambda = 2` became admissible. Your diagnosis that the
new tests used ordinary scales and never probed this boundary was also correct.

Two changes:

1. Variation is no longer inferred from the floating-point scale. It follows from
   the declared random coefficient and its design loading: the deviation-support
   machinery contributes `X[, j] * dev_range` for every declared column, and a
   zero loading contributes nothing on its own without any scale test. An
   arbitrarily small positive scale still yields unbounded normal support.
2. Every scale and dispersion on the R side now uses the template's
   transformations — `exp(clamp(log_s, -20, 20))`,
   `exp(clamp(log_m, -20, 20))` — and the `eta` interval is clamped to
   `[eta_floor, log(1e15)]` with `eta_floor = -35 - min(log(m), 0)` exactly as in
   `src/rpbnb_tmb.cpp`. The R-side constraint and the objective share one
   parameterization at every accepted start, which was the general form of your
   recommendation and is what makes the specific `-1000` case a non-event rather
   than a patched special case.

Verified: starting at `log_sd = -1000` in both margins now returns `[-1, 1]`, and
`lambda = 2` is outside it. A regression test pins that.

## Corrections to my previous response

For the record, two statements in `response_2026-08-08-07-36-52.md` were wrong
and are withdrawn:

- "The SML path is unchanged and keeps the finite-draw bound, which is the
  correct notion there." It is not the correct notion; it is the quadrature rule.
- "Treating a varying margin as spanning the full `(0, 1)` is exact for Normal
  coefficients and an over-approximation for lognormal ... conservative in the
  safe direction." True as far as it went, but I did not consider uniform or
  triangular, for which `(0,1)` is over-strict rather than conservative. That
  omission was live only on the Laplace path, which does not support those
  distributions, but the same helper now serves SML, where they are supported.

## What is still open

1. The Gaussian atomic is not thread-safe. The public-API cap makes it
   unreachable; it is not fixed.
2. The bounds are still **frozen at the starting values** and passed to the
   template as data. For normal and lognormal coefficients loaded in both
   margins the support bound is parameter-independent, so freezing is harmless
   there — which is now the common case. It still binds for a single varying
   margin and for uniform/triangular coefficients, where the bound moves with
   `beta`, `m` and `s`; those fits get the post-fit warning, not a corrected
   objective.
3. Gaussian tail cells whose NB2 CDF endpoints both reach the `safe_qnorm()`
   clamp still collapse to the `1e-300` floor.

Item 2 is materially narrower than it was two rounds ago, but the honest summary
is unchanged in kind: invalid optima are detected, not prevented, wherever the
bound depends on the parameters.
