## Verdict

The floor-only support scales fix the bounded-distribution defect, and the objective passed to `maxLik` now genuinely uses the interval frozen at the starting values. However, the code switches back to the interval recomputed at the optimum immediately after optimization. That makes the new admissibility guard incapable of detecting an escaped fit, changes the reported natural-scale lambda, and evaluates every standard-error path under a different objective from the one that produced the estimate.

## Findings

### P0 - The post-fit guard remaps lambda into the interval it is supposed to test

**Locations:** `R/fit_rpbnb.R:386-413`, `R/fit_rpbnb.R:510-515`, `R/fit_rpbnb.R:547-561`; compare `R/fit_rpbnb_tmb.R:622-643`.

The optimized objective maps `z_lambda` through `lam_frozen`, computed from the starting values. The post-fit check instead reconstructs `lam_hat_chk` by mapping the same `z_lambda` through `[lamLo_h, lamHi_h]`, the interval recomputed at the fitted parameters, and then asks whether that value lies inside `[lamLo_h, lamHi_h]`. For every finite, ordered interval this is true by construction: the interior logistic map always returns a point inside the interval through which it is mapped. Consequently, the warning described in the response cannot fire when the actual fitted lambda has left the admissible interval.

The same remapping is repeated for `lambda_hat`, so `fit$lambda` is not necessarily the lambda used to calculate `fit$logLik`. For example, with frozen bounds `[-2, 2]`, optimum bounds `[-0.5, 0.5]`, and `z_lambda = 2`, the optimized objective uses `lambda = 1.523185266`, which is inadmissible at the optimum. The current check and returned field instead use `lambda = 0.380796316` and report it as admissible.

Map `z_hat` through `lam_frozen` to obtain both the fitted lambda and the value checked against the interval at the optimum. Preserve the two intervals separately (as the TMB fit already does with `lambda_bounds` and `lambda_bounds_at_optimum`) and retain `lambda_admissible` on the fit object; the local value currently is not passed to `new_rpbnb_fit()`. Add a regression where the frozen interval is wider than the interval at the optimum and assert that the warning/flag uses the lambda from the optimized objective.

### P1 - OPG and Hessian covariance paths use a different interval from the optimized objective

**Locations:** `R/fit_rpbnb.R:424-496`, `R/halton_parallel.R:176-203`, `R/methods.R:183-191`.

Although `ll_fun()` now fixes the objective at `lam_frozen`, none of the standard-error paths retain that interval:

- `bnbr_rp_scores_cpp()` has no `lam_bounds` argument and recomputes the support interval from `par_hat`, so the OPG scores are not scores of the optimized objective when the interval moved.
- The analytic Hessian is explicitly called with `lamLo_h`/`lamHi_h`.
- The numeric Hessian closures are also explicitly built with `lamLo_h`/`lamHi_h`.

Thus the comments at lines 426-454 claiming the scores and Hessians use the frozen bounds of the actual objective are false for every parameter-dependent case this change is intended to fix. The resulting covariance estimates describe a reparameterized likelihood that was not optimized. In addition, `fit$bounds` is set to the optimum interval, and `summary.rpbnb_fit()` uses its width for the delta-method derivative of lambda, compounding the mismatch even if the covariance of `z_lambda` were corrected.

Pass `lam_frozen` to the score kernel and to both Hessian paths, and use its width for the reported lambda transformation and delta method. Keep the recomputed optimum interval only for the validity diagnostic. Add tests that move the support interval away from its starting value and verify (1) `colSums(scores)` equals the gradient of the frozen objective and (2) analytic/numeric curvature uses the same frozen interval.
